# Backend Rust (`src-tauri/`)

## Vues de comptes

- `show_active` ferme les autres vues avant de créer celle du compte actif, sous le verrou `views` : des changements de compte rapides tournent en parallèle. Pour changer de compte, modifier `store.active`, relâcher le verrou du store, puis appeler `show_active`.
- Ordre des verrous : `views` puis `store`, jamais l'inverse.
- La vue est masquée jusqu'à `PageLoadEvent::Finished` (`reveal`), avec un filet de sécurité de 8 s limité à la dernière vue créée (`generation`). Tout chemin d'erreur après `set_loading(app, true)` doit arrêter le loader.

## Pièges WebView2 / Tauri déjà rencontrés

- Créer une webview ou une fenêtre depuis une commande **synchrone** bloque l'application sous Windows. Toute commande qui peut en créer est déclarée `#[tauri::command(async)]`, et le verrou du `Mutex<Store>` est relâché avant de toucher aux webviews.
- Pour une fenêtre secondaire, utiliser `owner_raw` et non `parent_raw` : ce dernier crée une fenêtre enfant, masquée par les vues de comptes.
- Une vue de compte ne sait pas ouvrir de nouvel onglet (`target="_blank"`, `window.open`) : `open_link` ouvre les services Google dans la vue elle-même et tout autre site dans le navigateur par défaut.
- Un script de page ne peut pas lire une ressource qui redirige vers un autre domaine (l'origine devient `null`, refusée par Google) : c'est pourquoi une photo de profil privée n'est pas récupérable.

## `PROFILE_SCRIPT`

Injecté dans les pages Google ; ses sélecteurs dépendent du HTML de Google et peuvent casser. Il vérifie toutes les 3 s jusqu'à trouver le profil, puis toutes les minutes : ne pas réintroduire d'interrogation rapide permanente. La photo est transmise en `data:` URL (seul format accepté par `report_profile`).

## Permissions (à ne pas oublier en ajoutant une commande)

`build.rs` déclare la liste des commandes de l'application, ce qui rend **chaque commande interdite par défaut**. Une nouvelle commande doit être ajoutée à trois endroits : `generate_handler!` dans `main.rs`, la liste de `build.rs`, et la permission `allow-<nom-en-kebab-case>` dans le bon fichier de `src-tauri/capabilities/` :

- `sidebar.json` : commandes de gestion des comptes, pour la webview `sidebar`.
- `prompt.json` : aperçu, validation et annulation, pour les fenêtres `prompt-*`.
- `accounts.json` : seule capacité ouverte à du contenu distant (`https://*.google.com` dans les vues `acct-*`), limitée à `report_profile`. Cette commande déduit le compte de la webview appelante et valide ses arguments ; ne rien y ajouter sans la même prudence.

Une commande qui reçoit un identifiant de compte le vérifie dans le store avant tout usage (il peut servir à construire un chemin, comme `profiles/<id>`).

`src-tauri/permissions/autogenerated/` est régénéré à chaque build et ignoré par git.
